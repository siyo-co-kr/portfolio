## 배경

기존 RPA에는 유지보수 비용을 키우는 구조적 문제가 있었습니다.

1. **좌표 하드코딩** — EMR UI가 바뀔 때마다 수정이 필요했습니다. 기준점 기반 상대 좌표로 위치 이동에는 대응했지만, 배치 자체가 바뀌는 경우에는 근본적인 한계가 있었습니다.
2. **병원별 소스코드 분기** — 같은 EMR 프로그램을 제어하더라도 병원마다 소스코드가 따로 존재했습니다. 공통 수정도 병원마다 반복해야 했습니다.
3. **병원별 수동 배포** — 수정할 때마다 각 병원 PC에 원격 접속 → 로컬 변수 파일(좌표) 수정 → 빌드 → 배포를 반복해야 했습니다.

## 해결 방향

### ① 요소 기반 접근 — 좌표 하드코딩 제거

- Python **pywinauto**로 좌표가 아닌 **UI 요소(컨트롤) 단위로 접근**하는 구조로 전환
- 버튼·입력란을 이름, 타입, 식별자 등 속성으로 찾아 조작 → 위치가 바뀌어도 동작 유지

### ② 병원별 커스텀의 DB 이관 — 단일 소스코드화

- 병원별 커스텀 프로세스를 소스코드에서 **DB(설정 데이터)** 로 이동
- 모든 병원이 **같은 소스코드**를 사용하고, 병원·프로그램별 정보에 따라 동작이 달라지는 구조
- 코드는 공통 로직만, 병원별 차이는 데이터로 관리

## 동작 흐름(flow) 정의

기능의 동작 순서를 **JSON 데이터로 정의**하고, 공통 엔진이 이 데이터를 읽어 순서대로 실행합니다.

예) "예약" 기능: `예약 생성` 클릭 → `이름` 입력 → `날짜` 선택 → `저장` 클릭

```json
{
  "program": "DENTWEB",
  "function": "RESERVE",
  "flow": [
    { "auto_id": "예약생성", "action": "click" },
    { "auto_id": "이름input", "action": "textInput" },
    { "auto_id": "날짜선택", "action": "selectCombo" },
    { "auto_id": "save",     "action": "click" }
  ]
}
```

> 설명을 위한 단순화된 예시입니다.

- `program` + `function` — 어떤 EMR 프로그램의 어떤 기능인지 식별
- `auto_id` — pywinauto로 찾을 UI 요소의 식별자 (좌표 대신 요소로 접근)
- `action` — 해당 요소에 수행할 동작 (`click`, `textInput`, `selectCombo` 등)
- 화면 구성이나 순서가 바뀌면 **코드 수정 없이 flow 데이터만 수정**

## 기존 vs 개편안

```
[기존]  원격 접속 → 변수 파일 수정 → 빌드 → 배포   (× 병원 수만큼 반복)
[개편]  DB의 flow 데이터 수정                     (실행 시 자동 반영)
```

| 구분 | 기존 | 개편안 |
|---|---|---|
| 소스코드 | 병원별로 별도 존재 | 전 병원 단일 소스코드 |
| 병원별 커스텀 | 코드 안에서 분기·수정 | DB 설정 데이터로 관리 |
| 공통 수정 | 병원마다 반복 수정 | 한 번 수정으로 전체 반영 |
| 신규 병원 추가 | 코드 복사 후 수정 | DB에 설정 정보 등록 |
| 배포 | 수정할 때마다 병원별 빌드·배포 | 최초 1회 배포 |
| 변경 반영 | 원격 접속 → 로컬 변수 파일 수정 | DB의 flow 데이터 수정 |
| 화면 요소 접근 | 좌표 하드코딩 | UI 요소(컨트롤) 기반 |

## 진행 범위

기존 구조의 한계 분석, 기술 검토, 전환 설계까지 진행했습니다. (구현 전 단계에서 마무리)

## 기대 효과

- UI 변경 시 좌표 재설정 작업 제거
- 병원별 코드 분기 제거로 관리 포인트 단일화, 공통 수정 1회로 전체 반영
- 병원 PC 원격 접속·재빌드·재배포 없이 DB 수정만으로 변경 반영
- 신규 병원 세팅을 코드 작업이 아닌 설정 등록 중심으로 전환
